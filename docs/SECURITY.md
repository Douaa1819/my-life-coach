# Security model

The mobile app is an untrusted client. Anything compiled into it, including every `EXPO_PUBLIC_*` value, can be extracted by anyone who installs it. Data protection therefore lives in Supabase (Row Level Security and Edge Functions), never in the app.

## Enforced today (Phase 2)

| Area                | Measure                                                                                                                                                                                                                   | Where                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Keys in the app     | Only the project URL and the publishable key are read. The app refuses to start if the key starts with `sb_secret_` or is a JWT whose role is `service_role`.                                                             | `src/config/env.ts`                             |
| Env validation      | Zod validation at startup; `https://` required in release builds (`http://` allowed only in `__DEV__` for a local stack). Error lines name the variable and rule, never the value.                                        | `src/config/env.ts`, `public-env.ts`            |
| Fail closed         | Invalid config renders a configuration screen. Release builds show a generic message only.                                                                                                                                | `src/components/layout/config-error-screen.tsx` |
| Session storage     | Sessions are stored in the OS keystore via `expo-secure-store`, split into chunks to stay under the per-item size limit. Writes use a new generation of keys, so an interrupted write leaves the previous session intact. | `src/lib/supabase/chunked-storage.ts`           |
| Android backup      | The `expo-secure-store` config plugin adds backup and data-extraction rules that exclude SecureStore data from Auto Backup (verified in the prebuilt manifest).                                                           | `app.json`                                      |
| Android permissions | External storage and draw-over-apps permissions from the template are blocked.                                                                                                                                            | `app.json` `android.blockedPermissions`         |
| Auth flow           | PKCE flow, `detectSessionInUrl: false`, token refresh paused while the app is in the background.                                                                                                                          | `src/lib/supabase/client.ts`                    |
| Error display       | `ErrorState` shows a calm generic message and never renders raw errors.                                                                                                                                                   | `src/components/ui/state-views.tsx`             |
| Sample data         | Home data is sample data, labelled in the UI. Toggling a mission only changes the local cache; nothing is persisted and no XP is awarded on the client.                                                                   | `src/features/home/`                            |
| Secrets in Git      | `.env` is ignored; `.env.example` contains placeholders only.                                                                                                                                                             | `.gitignore`, `.env.example`                    |

The Android production bundle was scanned after export: it contains the publishable key (expected) and no secret key, service-role JWT or AI provider key.

## Enforced today (Phase 3: authentication and database)

| Area                | Measure                                                                                                                                                                                                                                                             | Where                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Passwords           | Only Supabase Auth sees passwords. The app keeps them in component state until submit and never stores or logs them. Rules (8–72 bytes, a letter and a digit) are enforced by Auth (`minimum_password_length`, `password_requirements`) and mirrored in Zod for UX. | `src/features/auth/auth.schema.ts`, `supabase/config.toml`                           |
| Email confirmation  | Required before the first sign-in. Links use PKCE (`?code=`), are single-use and are exchanged by the device that started the flow.                                                                                                                                 | `auth.api.ts`, `use-auth-link.ts`                                                    |
| Account enumeration | Sign-up, resend and reset return the same screen whether or not the email has an account; wrong email and wrong password give the same message.                                                                                                                     | `auth.api.ts`, `auth-errors.ts`                                                      |
| Error messages      | Auth and database errors are mapped to fixed messages by error code. Server messages, hints and details are never displayed or logged.                                                                                                                              | `auth-errors.ts`, `src/lib/supabase/data-access-error.ts`                            |
| Route protection    | `Stack.Protected` guards: tabs and app screens need a session, onboarding needs a session with onboarding incomplete, auth screens need no session. The splash screen stays up until the stored session is read, so there is no flash of the wrong screen.          | `src/components/navigation/root-navigator.tsx`, `src/features/auth/access.ts`        |
| Session lifecycle   | Sign-out removes the local session even when offline. A session lost without sign-out (expired or revoked refresh token) returns to Welcome with a "session expired" notice. | Password recovery   | A recovery link opens a recovery session that only reaches the reset screen until the password is changed or the user signs out. `secure_password_change` is on.                                                                                                    | `access.ts`, `reset-password-screen.tsx`                                             |
| Profiles table      | RLS on; select and update only where `auth.uid() = id`; no insert or delete for clients; column-level `update` grant on `display_name`, `avatar_url`, `timezone` only; `onboarding_completed`, `id` and timestamps are server-owned.                                | `supabase/migrations/20261103120000_create_profiles.sql`                             |
| Profile creation    | A `security definer` trigger on `auth.users` (in the non-exposed `private` schema, empty `search_path`) creates the row from the new user's id and sanitizes sign-up metadata.                                                                                      | same migration                                                                       |
| Database validation | Check constraints for name, avatar URL and time zone length; a trigger validates the time zone and forces `updated_at`.                                                                                                                                             | same migration                                                                       |
| Tests               | 24 pgTAP tests acting as two users, a two-user REST check and an end-to-end auth flow against the local stack.                                                                                                                                                      | `supabase/tests/database/`, `scripts/verify-rls.mjs`, `scripts/verify-auth-flow.mjs` |

## Rules for the next phases

These are requirements, not implemented yet.

1. **Row Level Security on every user-owned table.** Enable RLS at creation time with policies scoped to `auth.uid()`, for example `using (user_id = (select auth.uid()))` and the same `with check` on insert and update. No table is reachable without a policy. Add pgTAP tests acting as two users for each new table. See [`DATABASE.md`](DATABASE.md) for the planned tables.
2. **AI calls only through an Edge Function.** The function verifies the user's JWT, validates the request body with a schema, applies per-user rate limits and size limits, and holds the AI provider key as a function secret (`supabase secrets set`). The app never sees the key.
3. **The server decides outcomes.** XP, streaks, mission completion and any reward are computed by database functions or Edge Functions from validated inputs. AI output is treated as untrusted text: it can suggest, never authorize or write critical data.
4. **Validate on the backend.** Client-side Zod schemas are for UX. The same constraints must exist as database constraints or server-side validation.
5. **Errors.** Edge Functions return generic messages and stable error codes; details go to server logs only, without tokens or personal data.
6. **Least data.** Store only what coaching needs. Do not cache conversation history or health-like data on the device beyond the session unless there is a clear need.

## Known limitations

- **Web session storage** uses `localStorage`, which any script on the origin can read. Web is a development target here; a production web app would need a cookie-based session through a server.
- **Server-side enumeration on sign-up.** The app hides it, but the Auth API itself answers a duplicate sign-up for a confirmed account with `user_already_exists`, so a script calling the API directly can tell which emails are registered. Mitigations: keep Auth rate limits strict, enable CAPTCHA (Turnstile or hCaptcha) on sign-up, sign-in and reset before launch.
- **Leaked-password protection** (HaveIBeenPwned check) is a paid-plan Auth setting and is not enabled.
- **`exp://**` redirect URLs** are allowed so links work in Expo Go. Remove them, and the `localhost` URL, from the hosted project before release, leaving only `aicoach://**`.
- **Links open on another device** cannot complete the PKCE exchange; the user is asked to open the link on the phone or sign in. This is by design.
- **Default email sender.** Supabase's built-in SMTP is rate limited and for testing only; production needs custom SMTP.
- **Account deletion** is not available in the app yet. It needs an Edge Function using the admin API; profile rows cascade.
- **Onboarding flag** is server-owned, but nothing sets it yet. The onboarding phase must add a `security definer` function to complete onboarding and then set `ONBOARDING_REQUIRED` to `true`.
- **Home sample data.** Goals and missions on Home are still sample data, labelled "Sample plan · not saved". Only the name comes from the database.
- **Android device verification.** The auth flow was verified with automated tests, against the local Auth server, and in the web build; it still needs a run on a real Android device (deep links, keyboard, SecureStore). See [`SECURITY-TEST-PLAN.md`](SECURITY-TEST-PLAN.md).
- **`android.package` is not set.** It must be chosen before the first EAS build and cannot change after publishing.
- **Dependency audit.** `npm audit` reports 44 moderate and 1 low advisory, all from `glob`, `minimatch` and `deepmerge` inside tooling that runs in Node on the developer machine (Expo CLI and config plugins, ESLint, Jest), not inside the app bundle. Review them on each SDK upgrade; do not run `npm audit fix --force`, which replaces SDK-pinned versions.
- **Certificate pinning, jailbreak or root detection and app attestation** are not in place. Supabase rate limits and RLS remain the real protection.
